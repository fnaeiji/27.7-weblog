# PRD-01 — هسته وبلاگ، نقش‌ها و گردش تأیید محتوا

- **نسخه:** 1.0
- **وضعیت:** آماده برای تبدیل به Specification در Spec Kit
- **ترتیب اجرا:** فاز اول؛ پیش‌نیاز PRD-02 و PRD-03
- **نوع تحویل:** یک وب‌اپلیکیشن یکپارچه، قابل اجرا و تست در محیط محلی
- **زبان رابط کاربری:** فارسی و راست‌چین؛ محتوای مقاله می‌تواند فارسی یا انگلیسی باشد
- **منبع تصمیم‌های مشترک:** `ROADMAP-and-SpecKit-Guide_FA.md` در بسته تحویلی

## 1. خلاصه

ساخت هسته یک وبلاگ با صفحات عمومی و پنل مدیریت محتوا. سه نقش انسانی وجود دارد: **نویسنده (AUTHOR)**، **ویراستار (EDITOR)** و **مدیر (ADMIN)**. نویسنده پیش‌نویس ایجاد می‌کند؛ ویراستار محتوا را بررسی و در صورت نیاز اصلاح یا برای تغییر برمی‌گرداند؛ مدیر تصمیم نهایی انتشار را می‌گیرد. بازدیدکننده ناشناس فقط مقاله‌های منتشرشده را مشاهده می‌کند.

این فاز باید بدون هیچ سرویس AI، بدون API Key و بدون اتصال به اینترنت برای اجرای برنامه و تست‌های آن کامل کار کند. AI در PRD-02 اضافه می‌شود.

## 2. اهداف

1. داشتن وبلاگ عمومی قابل استفاده و پنل محتوای محافظت‌شده.
2. اعمال نقش‌ها و مجوزها در سمت سرور، نه فقط مخفی‌کردن دکمه‌ها در UI.
3. تعریف گردش روشن از پیش‌نویس تا بازبینی ویراستار و تأیید نهایی مدیر.
4. حفظ نسخه‌های مقاله و سابقه تغییر وضعیت‌ها.
5. جلوگیری از نمایش پیش‌نویس، محتوای در حال بازبینی و یادداشت‌های داخلی به بازدیدکننده عمومی.
6. فراهم‌کردن یک پایه ساده که بعداً قابلیت‌های AI بدون بازنویسی هسته به آن اضافه شوند.

## 3. خارج از محدوده این فاز

- تولید، بازنویسی، ویراستاری یا چت با AI؛ این موارد در PRD-02 و PRD-03 هستند.
- چندسازمانی، چند وبلاگ، همکاری هم‌زمان، زمان‌بندی انتشار، دیدگاه، لایک، خبرنامه، پرداخت و آپلود رسانه.
- microservices، صف پیام، معماری توزیع‌شده یا استقرار ابری پیچیده.
- API عمومی برای مصرف‌کنندگان ثالث و الزام Swagger به‌عنوان رابط اصلی. در این MVP رابط اصلی UI ساده با Thymeleaf است.

## 4. فناوری و تصمیم‌های اجرایی

- Java 17 یا بالاتر.
- Spring Boot 3.x و Maven.
- Spring MVC و Thymeleaf برای رابط کاربری سروررندرشده.
- Spring Security برای ورود، نشست و مجوزها.
- Spring Data JPA.
- H2 برای اجرای پیش‌فرض محلی و تست؛ پشتیبانی از PostgreSQL با profile و تنظیمات مجزا.
- JUnit 5 و Spring Boot Test؛ تست‌ها نباید اینترنت یا سرویس بیرونی بخواهند.
- یک برنامه یکپارچه (modular monolith)؛ microservice نساز.
- Markdown مقاله‌ها باید پیش از تبدیل به HTML پاک‌سازی شود. HTML/JavaScript ناامن نباید اجرا شود.

جزئیات نسخه‌های دقیق کتابخانه‌ها و ساختار package در `plan` تعیین شود؛ از اضافه‌کردن dependency غیرضروری خودداری شود.

## 5. نقش‌ها و مجوزها

### 5.1 بازدیدکننده ناشناس

- فقط فهرست مقاله‌های `PUBLISHED` و صفحه جزئیات آن‌ها را می‌بیند.
- نباید بتواند با حدس‌زدن ID یا slug به محتوای غیرمنتشرشده برسد.
- به پنل، نسخه‌ها، تاریخچه گردش کار و یادداشت‌های داخلی دسترسی ندارد.

### 5.2 نویسنده (`AUTHOR`)

- می‌تواند مقاله جدید ایجاد کند.
- می‌تواند پیش‌نویس‌های متعلق به خودش را ویرایش و ذخیره کند.
- می‌تواند مقاله خود را برای بررسی ویراستار ارسال کند.
- می‌تواند مقاله‌ای را که برای اصلاح به او برگردانده شده ویرایش و دوباره ارسال کند.
- می‌تواند نسخه‌ها و بازخوردهای مربوط به مقاله‌های مجاز خودش را ببیند.
- نمی‌تواند بازبینی ویراستار را نهایی کند، مقاله را منتشر/لغو انتشار کند یا نقش کاربران را تغییر دهد.
- مالکیت مقاله با شناسه کاربر ثبت‌شده در `author_id` مشخص می‌شود؛ مالکیت نباید از پارامتر ارسالی مرورگر پذیرفته شود.

### 5.3 ویراستار (`EDITOR`)

- صف مقالات `IN_EDITORIAL_REVIEW` را مشاهده می‌کند.
- می‌تواند مقاله ارسال‌شده را بخواند و اصلاح محتوایی انجام دهد.
- می‌تواند با یادداشت اجباری، مقاله را به `CHANGES_REQUESTED` برگرداند.
- می‌تواند پس از بازبینی آن را به `PENDING_ADMIN_APPROVAL` بفرستد.
- نمی‌تواند مستقیماً منتشر یا لغو انتشار کند و نمی‌تواند نقش کاربر را تغییر دهد.
- هر ویرایش ویراستار باید به‌عنوان revision جدا ذخیره شود و در تاریخچه قابل تشخیص باشد.

### 5.4 مدیر (`ADMIN`)

- به پنل و همه مقاله‌ها دسترسی مدیریتی دارد.
- می‌تواند کاربران را ایجاد، غیرفعال و به نقش‌های `AUTHOR`، `EDITOR` یا `ADMIN` منصوب کند.
- تنها نقشی است که می‌تواند مقاله `PENDING_ADMIN_APPROVAL` را منتشر کند یا مقاله منتشرشده را از انتشار خارج کند.
- می‌تواند در صورت رد نهایی، مقاله را با یادداشت به نویسنده/ویراستار برگرداند.
- نمی‌تواند با یک کلیک مقاله‌ای را که از گردش بررسی عبور نکرده مستقیماً منتشر کند. در صورت ویرایش مقاله در وضعیت انتظار تأیید، باید گردش بازبینی از نو انجام شود.
- برنامه نباید اجازه غیرفعال‌کردن یا تنزل نقش آخرین مدیر فعال را بدهد.

**قاعده امنیتی:** کنترل دسترسی برای هر عملیات هم در لایه کاربردی/سرویس و هم در مرز وب اعمال شود. مخفی‌کردن دکمه به‌تنهایی کنترل دسترسی محسوب نمی‌شود.

## 6. گردش وضعیت مقاله

وضعیت‌های MVP:

- `DRAFT`: پیش‌نویس قابل ویرایش.
- `IN_EDITORIAL_REVIEW`: منتظر اقدام ویراستار.
- `CHANGES_REQUESTED`: اصلاح لازم است؛ یادداشت علت باید ذخیره شده باشد.
- `PENDING_ADMIN_APPROVAL`: ویراستار بررسی را انجام داده و مقاله منتظر تصمیم مدیر است.
- `PUBLISHED`: منتشرشده و قابل مشاهده عمومی.

انتقال‌های مجاز:

1. `DRAFT` → `IN_EDITORIAL_REVIEW`: نویسنده، ویراستار یا مدیرِ مجاز ارسال می‌کند.
2. `IN_EDITORIAL_REVIEW` → `CHANGES_REQUESTED`: ویراستار با یادداشت اجباری.
3. `IN_EDITORIAL_REVIEW` → `PENDING_ADMIN_APPROVAL`: ویراستار پس از بررسی.
4. `CHANGES_REQUESTED` → `IN_EDITORIAL_REVIEW`: پس از اصلاح و ارسال مجدد نویسنده/ویراستار مجاز.
5. `PENDING_ADMIN_APPROVAL` → `PUBLISHED`: فقط مدیر و فقط اگر نسخه تأییدشده همان نسخه جاری باشد.
6. `PENDING_ADMIN_APPROVAL` → `CHANGES_REQUESTED`: مدیر با یادداشت توضیحی.
7. `PUBLISHED` → `DRAFT`: فقط با اقدام صریح مدیر برای لغو انتشار؛ مقاله بلافاصله از صفحات عمومی حذف می‌شود و برای انتشار مجدد باید کل گردش بررسی از نو طی شود.

### قوانین نسخه و وضعیت

- هر ذخیره‌ای که title، excerpt، bodyMarkdown یا tags را تغییر دهد، یک `ArticleRevision` جدید با شماره نسخه افزایشی ایجاد می‌کند. ذخیره بدون تغییر محتوا revision جدید نمی‌سازد.
- هر بار مقاله پس از بررسی ویراستار تغییر کند، وضعیت پیشین معتبر برای ادامه گردش نیست. اگر مقاله در `IN_EDITORIAL_REVIEW` یا `PENDING_ADMIN_APPROVAL` ویرایش شد، باید به `DRAFT` یا `CHANGES_REQUESTED` برگردد و دوباره ارسال شود.
- تأیید ویراستار و تصمیم انتشار مدیر باید به **شناسه دقیق revision** متصل باشد، نه صرفاً شناسه مقاله یا شماره وضعیت.
- هیچ endpoint یا مسیر UI نباید بتواند شرط انتشار را دور بزند.
- عنوان/خلاصه/متن/برچسب‌های مقاله منتشرشده مستقیماً تغییر نمی‌کنند. ابتدا باید لغو انتشار شود، سپس ویرایش و بازبینی مجدد انجام شود.

## 7. نیازمندی‌های عملکردی

### FR-01 — ورود و مدیریت کاربران

- پنل مدیریتی نیازمند ورود باشد.
- ثبت‌نام عمومی وجود ندارد.
- نخستین مدیر از متغیرهای محیطی `APP_BOOTSTRAP_ADMIN_USERNAME` و `APP_BOOTSTRAP_ADMIN_PASSWORD` ساخته شود، فقط اگر هیچ مدیر موجودی نیست.
- رمز عبور با الگوریتم امن و استاندارد Spring Security (مانند BCrypt) ذخیره شود؛ متن خام رمز عبور هرگز ذخیره نشود.
- مدیر بتواند کاربران و نقش‌های مجاز را مدیریت کند. کاربر غیرفعال نتواند وارد شود.
- هیچ رمز واقعی در repository یا `.env.example` قرار نگیرد.

### FR-02 — صفحات عمومی

- صفحه اصلی فقط مقاله‌های منتشرشده را نمایش دهد، با عنوان، خلاصه، تاریخ انتشار و slug.
- صفحه جزئیات مقاله شامل عنوان، خلاصه، متن، برچسب‌ها و تاریخ انتشار باشد.
- slug یکتا باشد؛ تکرار slug با خطای قابل فهم رد شود.
- برای slug ناموجود یا مقاله منتشرنشده پاسخ 404 ارائه شود؛ پاسخ نباید وجود پیش‌نویس را افشا کند.
- Markdown به HTML امن تبدیل شود و HTML ناامن پاک‌سازی/خنثی شود.

### FR-03 — ایجاد و ویرایش مقاله

- فیلدهای محتوا: `title`، `slug`، `excerpt`، `bodyMarkdown` و `tags`.
- عنوان و متن اصلی الزامی باشند؛ slug در صورت تولید خودکار باید یکتا شود و مدیر/کاربر مجاز بتواند آن را بررسی کند.
- فرم ایجاد اولیه مقاله با وضعیت `DRAFT` ذخیره شود.
- خطای اعتبارسنجی باید کنار فرم نمایش داده شود و داده‌های واردشده از بین نروند.
- author_id فقط توسط سرویس بر اساس کاربر واردشده تعیین شود.

### FR-04 — ارسال و بازبینی ویراستار

- نویسنده بتواند پیش‌نویس مجاز را برای بررسی ارسال کند.
- ویراستار صف بازبینی و جزئیات مقاله را ببیند.
- ثبت `CHANGES_REQUESTED` نیازمند یادداشت غیرخالی است.
- انتقال به `PENDING_ADMIN_APPROVAL` باید در تاریخچه ثبت شود.
- تصمیم‌ها و یادداشت‌های قبلی حذف یا بی‌صدا بازنویسی نشوند.

### FR-05 — تأیید نهایی و انتشار

- دکمه انتشار تنها در صورت `PENDING_ADMIN_APPROVAL` و تطابق revision جاری با revision بررسی‌شده فعال باشد.
- سرور دوباره این شرط‌ها را پیش از انتشار اعتبارسنجی کند.
- لغو انتشار توسط مدیر، مقاله را از فهرست و مسیر عمومی خارج کند.
- تاریخ انتشار فقط هنگام انتشار موفق ثبت شود.

### FR-06 — تاریخچه و ممیزی

- برای هر مقاله، revisionها و رخدادهای تغییر وضعیت نمایش داده شوند.
- هر رخداد گردش کار حداقل actor، action، وضعیت قبل/بعد، یادداشت اختیاری و زمان را نگه دارد.
- شناسه کاربر عامل تغییر نباید از ورودی کاربر/مرورگر پذیرفته شود.

### FR-07 — خطا و تجربه کاربری

- خطاهای validation و دسترسی با پیام قابل فهم و بدون stack trace نمایش داده شوند.
- فرم‌ها در موبایل و دسکتاپ قابل استفاده و برای فارسی RTL باشند.
- وضعیت مقاله در داشبورد واضح باشد.
- برای صفحه‌های فهرست، جزئیات، ورود، داشبورد، ایجاد/ویرایش، صف ویراستار، تاریخچه و مدیریت کاربران UI ساده وجود داشته باشد.

## 8. مدل داده مفهومی

جزئیات نهایی schema در مرحله `plan` تعیین شود؛ حداقل موجودیت‌ها:

- `User`: شناسه، username یکتا، passwordHash، role، active، createdAt.
- `Article`: شناسه، author_id، وضعیت، نسخه جاری، زمان ایجاد/ویرایش/انتشار.
- `ArticleRevision`: شناسه، article_id، revisionNumber، snapshot فیلدهای محتوا، createdBy، createdAt.
- `WorkflowEvent`: شناسه، article_id، revision_id (در صورت وجود)، actor_id، action، fromStatus، toStatus، note، createdAt.

استفاده از enumهای مشخص برای role و status الزامی است. روابط، حذف کاربر و رفتار تاریخی آن‌ها باید طوری طراحی شوند که سوابق مقاله از بین نروند؛ ترجیحاً غیرفعال‌سازی به‌جای حذف فیزیکی کاربر.

## 9. صفحات اصلی

- عمومی: `/`، `/posts/{slug}`، صفحه 404.
- ورود: `/login` و خروج امن.
- نویسنده/مدیر: داشبورد، ایجاد مقاله، ویرایش پیش‌نویس‌های مجاز، تاریخچه.
- ویراستار: صف بازبینی، جزئیات/ویرایش مقاله، ثبت درخواست اصلاح یا ارسال برای تأیید مدیر.
- مدیر: داشبورد سراسری، انتشار/لغو انتشار، مدیریت کاربران و نقش‌ها.

نام دقیق routeها می‌تواند در `plan` تعیین شود؛ رفتار امنیتی و معنای مسیرها نباید تغییر کند.

## 10. معیارهای پذیرش

- **AC-01:** برنامه با Java و Maven در حالت محلی و بدون API Key یا اینترنت اجرا شود.
- **AC-02:** در صورت نبود مدیر، مدیر اولیه با env ساخته شود؛ در اجرای بعدی مدیر تکراری ساخته نشود.
- **AC-03:** کاربر ناشناس نتواند هیچ صفحه مدیریتی را ببیند و به login هدایت شود.
- **AC-04:** نویسنده نتواند مقاله متعلق به نویسنده دیگر را بخواند یا ویرایش کند، حتی با تغییر ID در URL یا ارسال request دستی.
- **AC-05:** نویسنده بتواند مقاله بسازد و آن را برای بررسی ارسال کند.
- **AC-06:** ویراستار بتواند درخواست اصلاح با یادداشت ثبت کند یا مقاله را برای تأیید مدیر ارسال کند.
- **AC-07:** نویسنده و ویراستار نتوانند مقاله را منتشر کنند.
- **AC-08:** مدیر نتواند مقاله‌ای را که در وضعیت مناسب نیست منتشر کند.
- **AC-09:** هر تغییر محتوایی یک revision نگه دارد و revision قبلی دست‌نخورده بماند.
- **AC-10:** ویرایش پس از بررسی باعث شود اجازه انتشار قبلی معتبر نباشد.
- **AC-11:** مقاله منتشرنشده در فهرست عمومی و صفحه جزئیات عمومی دیده نشود.
- **AC-12:** لغو انتشار مقاله را بلافاصله از خروجی عمومی حذف کند.
- **AC-13:** slug تکراری رد شود.
- **AC-14:** محتوای Markdown شامل script یا HTML ناامن در صفحه عمومی اجرا نشود.
- **AC-15:** آخرین مدیر فعال نتواند غیرفعال یا تنزل نقش داده شود.
- **AC-16:** تست‌های اصلی گردش کار و مجوزها با H2/Fake اجرا شوند و نیازمند شبکه نباشند.

## 11. تست‌های خودکار اجباری

حداقل تست‌های واحد/یکپارچه برای این موارد ایجاد شود:

1. انتقال‌های مجاز و رد انتقال‌های غیرمجاز وضعیت.
2. تست دسترسی ناشناس، AUTHOR، EDITOR و ADMIN به عملیات حساس.
3. جلوگیری از دسترسی نویسنده به مقاله نویسنده دیگر.
4. ایجاد revision هنگام تغییر محتوا و عدم ایجاد revision برای ذخیره بدون تغییر.
5. جلوگیری از انتشار بدون ارسال ویراستار و تأیید مدیر.
6. باطل‌شدن اعتبار revision پس از ویرایش.
7. فیلتر عمومی بر اساس `PUBLISHED`.
8. لغو انتشار و حذف از صفحات عمومی.
9. یکتایی slug.
10. امن‌بودن رندر Markdown.
11. جلوگیری از غیرفعال‌سازی آخرین مدیر فعال.

## 12. تعریف پایان کار (DoD)
