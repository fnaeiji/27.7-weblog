# PRD-02 — ابزارهای AI برای نگارش، ویراستاری و گزارش بازبینی

- **نسخه:** 1.0
- **وضعیت:** آماده برای تبدیل به Specification در Spec Kit
- **ترتیب اجرا:** فاز دوم؛ فقط پس از تکمیل و تست PRD-01
- **وابستگی سخت:** نقش‌ها، مقاله‌ها، نسخه‌بندی و گردش کار تعریف‌شده در PRD-01
- **هدف:** اضافه‌کردن AI به‌عنوان ابزار کمکی؛ تصمیم‌های انسانی و مجوزهای هسته تغییر نمی‌کنند

## 1. خلاصه

این feature ابزارهای AI را به وبلاگ اضافه می‌کند تا کاربر مجاز بتواند از موضوع، پیش‌نویس تولید کند؛ نسخه فعلی مقاله را برای بازخورد ویراستاری بررسی کند؛ و با انتخاب آگاهانه خود از AI بخواهد نسخه پیشنهادی جدیدی بسازد. AI نه جایگزین ویراستار انسانی است و نه اختیار تأیید نهایی، تغییر گردش کار، انتشار یا لغو انتشار دارد.

دو کامپوننت مستقل در لایه کاربردی تعریف می‌شوند: `WritingAgent` برای تولید/بازنویسی پیش‌نویس و `ReviewAgent` برای تولید گزارش ارزیابی. هر کدام prompt، قرارداد ورودی/خروجی، provider، مدل و تنظیمات اتصال مستقل دارد. هیچ‌کدام دیگری را مستقیماً فراخوانی نمی‌کند؛ هماهنگی فقط از طریق برنامه و با درخواست صریح کاربر انجام می‌شود.

## 2. اهداف

1. تولید پیش‌نویس اولیه از موضوع و دستورالعمل اختیاری.
2. دریافت گزارش ویراستاری ساختاریافته از نسخه دقیق مقاله.
3. امکان انتخاب بازخوردها و درخواست بازنویسی با اقدام صریح کاربر.
4. حفظ متن و revisionهای قبلی در همه حالت‌ها.
5. اجرای کامل جریان AI در حالت Mock بدون API Key و اینترنت.
6. پشتیبانی اختیاری از provider سازگار با API چت OpenAI، با تنظیمات مستقل دو agent.
7. ثبت تاریخچه اجرا و گزارش‌ها بدون افشای کلید یا داده محرمانه در log.

## 3. خارج از محدوده

- انتشار خودکار یا تصمیم نهایی به‌جای مدیر.
- اجرای agent-to-agent، حافظه مشترک میان agentها، RAG، جست‌وجوی وب یا راستی‌آزمایی قطعی واقعیت‌ها.
- آموزش مدل یا مدیریت مدل اختصاصی.
- بازنویسی پنهانی محتوا در پس‌زمینه یا اجرای خودکار بازبینی/اصلاح پشت سر هم.
- پشتیبانی از providerهای اختصاصی متعدد با SDKهای جدا؛ در MVP قرارداد OpenAI-compatible کافی است.

## 4. اصول غیرقابل نقض

1. مدل خروجی نامطمئن است؛ همه خروجی‌ها پیش از ذخیره اعتبارسنجی شوند.
2. AI هیچ دسترسی مستقیمی به repository، دیتابیس یا عملیات انتشار ندارد؛ فقط ورودی و خروجی قرارداد خودش را دریافت می‌کند.
3. `ReviewAgent` فقط گزارش تولید می‌کند و حق نوشتن یا تغییر فیلدهای مقاله، وضعیت مقاله یا revision را ندارد.
4. خروجی verdict برابر `APPROVED` از AI **به معنی تأیید انسانی یا مجوز انتشار نیست**. مجوزهای workflow در PRD-01 همچنان حاکم‌اند.
5. هر تغییر محتوایی با AI فقط بعد از preview و تأیید صریح کاربر اعمال می‌شود و یک revision جدید می‌سازد.
6. خطا، timeout، پاسخ خالی یا خروجی نامعتبر نباید متن موجود، revisionها یا وضعیت انتشار را خراب کند.
7. متن مقاله و دستورالعمل کاربر ممکن است حاوی prompt injection باشند؛ آن‌ها داده ورودی‌اند، نه مجوز تغییر نقش یا دورزدن قواعد سیستم.

## 5. نقش‌ها و دسترسی‌ها

- `AUTHOR`: می‌تواند روی مقاله‌های مجاز خود تولید/بازنویسی و گزارش AI اجرا کند.
- `EDITOR`: می‌تواند روی مقالات مجاز در گردش ویراستاری از ابزارهای AI استفاده کند.
- `ADMIN`: می‌تواند قابلیت‌های AI را روی همه مقاله‌ها اجرا کند.
- کاربر ناشناس نمی‌تواند endpoint یا صفحه AI را اجرا کند.

سرویس‌ها باید مجوزهای PRD-01 را دوباره بررسی کنند. فرستادن `articleId` یا `revisionId` در request به‌تنهایی دسترسی ایجاد نمی‌کند. هر عملیات روی مقاله `PUBLISHED` باید ممنوع باشد تا وقتی مدیر آن را از انتشار خارج نکرده باشد.

## 6. گردش کارهای AI

### 6.1 تولید پیش‌نویس

1. کاربر مجاز موضوع اجباری را وارد می‌کند.
2. لحن، مخاطب، زبان و طول تقریبی اختیاری هستند.
3. برنامه فقط `WritingAgent` را اجرا می‌کند.
4. خروجی ساختاریافته اعتبارسنجی می‌شود.
5. پس از موفقیت، مقاله با وضعیت `DRAFT` و revision اولیه ذخیره می‌شود.
6. UI برچسب `AI/Mock` یا `AI/Real` و وضعیت اجرای مدل را نشان می‌دهد.

### 6.2 بازبینی AI

1. کاربر یک revision مشخص را انتخاب می‌کند.
2. برنامه snapshot همان revision را به `ReviewAgent` می‌دهد.
3. گزارش معتبر در `ReviewReport` ذخیره و با revision دقیق مرتبط می‌شود.
4. گزارش در UI نمایش داده می‌شود؛ مقاله و وضعیت workflow تغییر نمی‌کند.
5. اگر اجرای مدل خطا بدهد، گزارش موفق ساخته نمی‌شود و محتوای موجود حفظ می‌شود.

### 6.3 بازنویسی براساس بازخورد

1. کاربر گزارش را می‌خواند و یک یا چند finding را انتخاب می‌کند یا دستور اصلاح می‌نویسد.
2. برنامه فقط با کلیک صریح «ساخت نسخه پیشنهادی» `WritingAgent` را اجرا می‌کند.
3. خروجی به شکل preview قبل/بعد نمایش داده می‌شود و هنوز متن اصلی را جایگزین نمی‌کند.
4. کاربر می‌تواند آن را رد کند یا صریحاً «اعمال به‌عنوان نسخه جدید» را بزند.
5. در صورت اعمال، revision جدید ساخته می‌شود و سابقه و گزارش قبلی باقی می‌ماند؛ گزارش قدیمی برای revision جدید مجوز محسوب نمی‌شود.
6. اگر وضعیت workflow در زمان اجرا تغییر کرده باشد یا revision فعلی با revision ورودی برابر نباشد، عملیات اعمال باید رد شود و کاربر نسخه جدید را دوباره بررسی کند.

## 7. نیازمندی‌های عملکردی

### FR-01 — قرارداد `WritingAgent`

ورودی شامل یکی از حالت‌های `GENERATE_DRAFT` یا `REWRITE_DRAFT`، topic یا snapshot مقاله، دستورالعمل کاربر و بازخوردهای انتخاب‌شده است. خروجی JSON معتبر با فیلدهای زیر باشد:

```json
{
  "title": "عنوان مقاله",
  "excerpt": "خلاصه کوتاه",
  "bodyMarkdown": "متن مقاله با Markdown",
  "tags": ["java", "ai"]
}
```

- فیلدهای ضروری و نوع داده‌ها اعتبارسنجی شوند؛ `tags` آرایه‌ای از رشته‌هاست.
- topic در حالت `GENERATE_DRAFT` اجباری است.
- خروجی ناقص، JSON نامعتبر یا مقدار خارج از محدودیت‌ها نباید به‌عنوان موفقیت ذخیره شود.
- مدل نباید slug یکتا یا workflow status را مرجع حقیقت قرار دهد؛ تولید/اعتبارسنجی slug توسط برنامه انجام شود.

### FR-02 — قرارداد `ReviewAgent`

خروجی ساختاریافته پیشنهادی:

```json
{
  "verdict": "NEEDS_CHANGES",
  "score": 76,
  "strengths": ["ساختار کلی روشن است"],
  "findings": [
    {
      "severity": "MEDIUM",
      "location": "بخش دوم",
      "issue": "ادعای مهمی پشتوانه کافی در متن ندارد",
      "suggestion": "منبع اضافه کنید یا ادعا را محتاطانه‌تر بنویسید"
    }
  ]
}
```

- `verdict` فقط `APPROVED` یا `NEEDS_CHANGES` باشد.
- `score` عدد صحیح 0 تا 100 باشد.
- `severity` یکی از `HIGH`، `MEDIUM`، `LOW` باشد.
- `strengths` و `findings` آرایه معتبر باشند؛ جزئیات هر finding به‌صورت schema-validated ذخیره شود.
- معیارهای بازبینی: ارتباط با موضوع، وضوح/خوانایی، املا و یکدستی لحن، تناسب عنوان و خلاصه با متن و ادعاهای مهم بدون پشتوانه کافی.
- AI نباید ادعا کند حقیقت را از منابع بیرونی قطعی راستی‌آزمایی کرده است.
- اگر ساختار گزارش معتبر نباشد، اجرای بازبینی failed می‌شود و هیچ تأیید workflow ثبت نمی‌شود.

### FR-03 — استقلال agentها

- قراردادها و پیاده‌سازی‌های `WritingAgent` و `ReviewAgent` جدا باشند.
- prompt سیستم، provider، مدل، endpoint، API key و timeout هر کدام مستقل تنظیم شوند.
- هیچ سرویس agent نباید سرویس agent دیگر را صدا بزند.
- گردش کار AI از controller/application service شروع شود و هر اقدام تنها در پاسخ به عملیات صریح کاربر اجرا شود.
- `ReviewAgent` نباید repository نوشتنی `Article` داشته باشد؛ معماری باید این محدودیت را قابل آزمون کند. ورودی آن snapshot تغییرناپذیر و خروجی آن report باشد.

### FR-04 — حالت Mock و provider واقعی

برای هر agent، تنظیمات مستقل زیر پشتیبانی شود:

- `AI_WRITER_PROVIDER=MOCK|OPENAI_COMPATIBLE`
- `AI_WRITER_BASE_URL`
- `AI_WRITER_MODEL`
- `AI_WRITER_API_KEY`
- `AI_WRITER_TIMEOUT_MS`
- `AI_WRITER_SYSTEM_PROMPT` (اختیاری؛ پیش‌فرض امن در برنامه)
- متغیرهای متناظر `AI_REVIEW_*` برای ReviewAgent.

قواعد:

- پیش‌فرض هر دو provider برابر `MOCK` باشد.
- برای API Key فقط از محیط اجرا خوانده شود؛ در repository، UI، response، exception message یا log چاپ نشود.
- از HTTP client سازگار با Java 17 استفاده شود و timeoutهای اتصال/پاسخ محدود باشند.
- endpoint OpenAI-compatible از configuration قابل تعیین باشد؛ فرض نکن همه providerها تنظیمات پیش‌فرض یکسان دارند.
- پاسخ provider باید قبل از تبدیل به DTO و ذخیره validate شود.
- خطاهای 4xx/5xx، timeout، rate limit، پاسخ خالی و JSON نامعتبر به خطای کاربردی امن تبدیل شوند.
- در حالت Mock نتایج deterministic و برای تست قابل پیش‌بینی باشند؛ UI مشخص کند نتیجه Mock است.
- لازم نیست حالت real برای اجرای تست‌ها تنظیم یا فراخوانی شود.

### FR-05 — گزارش و تاریخچه اجرا

برای هر اجرا حداقل موارد زیر ثبت شود:

- شناسه اجرا، نوع agent، articleId (در صورت وجود)، revision ورودی، operation، provider/model غیرمحرمانه، startedAt، duration، وضعیت `SUCCESS|FAILED` و کد خطای عمومی.
- برای بازبینی موفق، report به revision ورودی متصل شود.
- secretها و raw authorization headers در لاگ/دیتابیس ذخیره نشوند.
- ثبت محتوای کامل prompt یا پاسخ خام provider الزامی نیست؛ از ثبت داده غیرضروری اجتناب شود.

### FR-06 — UI

- در فرم مقاله دکمه تولید از موضوع و فیلدهای دستورالعمل اختیاری باشد.
- در صفحه مقاله دکمه «بازبینی AI» و بخش گزارش/تاریخچه گزارش‌ها وجود داشته باشد.
- روی هر گزارش، findingها و پیشنهادها قابل انتخاب باشند.
- preview بازنویسی قبل از اعمال نمایش داده شود.
- زمان اجرای طولانی، در حال اجرا/موفق/ناموفق بودن واضح باشد؛ کلیک دوباره نباید درخواست تکراری ناخواسته بسازد.
- برای خطاهای AI، پیام انسانی نمایش داده شود و متن فرم یا ذخیره قبلی از بین نرود.

## 8. مدل داده تکمیلی

حداقل موجودیت‌های جدید:

- `ReviewReport`: articleId، revisionId، verdict، score، strengths، findings ساختاریافته، executionId، createdAt.
- `AgentRun`: agentType، operation، articleId/revisionId، provider/model، start/end یا duration، status، safeErrorCode.

ساختار ذخیره‌سازی JSON تنها در صورتی استفاده شود که برای پایگاه داده منتخب و queryهای مورد نیاز مناسب باشد؛ تصمیم نهایی در plan و migrationها مشخص شود. تغییرات schema باید سازگار با H2 و PostgreSQL باشند.

## 9. معیارهای پذیرش

- **AC-01:** برنامه و جریان AI در حالت Mock بدون API Key اجرا شوند.
- **AC-02:** تولید مقاله Mock معتبر، قابل ویرایش و در وضعیت DRAFT ذخیره شود.
- **AC-03:** topic خالی رد شود و پیام قابل فهم بدهد.
- **AC-04:** خروجی نامعتبر WritingAgent ذخیره نشود و متن/داده قبلی محفوظ بماند.
- **AC-05:** ReviewAgent روی revision انتخاب‌شده report ساختاریافته ثبت کند.
- **AC-06:** ReviewAgent نتواند title، excerpt، bodyMarkdown، tags، status یا revision جاری را تغییر دهد.
- **AC-07:** verdict برابر APPROVED از AI به‌تنهایی اجازه عبور به `PENDING_ADMIN_APPROVAL` یا `PUBLISHED` ندهد.
- **AC-08:** درخواست بازنویسی فقط پس از اقدام صریح انسان انجام شود.
- **AC-09:** preview بازنویسی متن اصلی را تغییر ندهد.
- **AC-10:** اعمال بازنویسی revision جدید بسازد و گزارش قدیمی را حفظ کند.
- **AC-11:** گزارش AI برای revision قدیمی مجوزی برای نسخه فعلی تلقی نشود.
- **AC-12:** خطای provider، timeout یا JSON نامعتبر status تأیید/انتشار ایجاد نکند و متن را از بین نبرد.
- **AC-13:** تنظیمات Writer و Reviewer مستقل باشند؛ تغییر یکی، دیگری را تغییر ندهد.
- **AC-14:** API key در log، exception، HTML، response یا فایل repository ظاهر نشود.
- **AC-15:** کاربر بدون دسترسی نتواند با تغییر articleId/revisionId عملیات AI اجرا کند.
- **AC-16:** تست‌ها بدون اینترنت و API واقعی اجرا شوند.

## 10. تست‌های خودکار اجباری

1. تست قرارداد و validation خروجی هر agent.
2. تست deterministic Mock برای تولید و گزارش بازبینی.
3. تست عدم تغییر مقاله توسط ReviewAgent.
4. تست اینکه گزارش AI با revision دقیق پیوند دارد.
5. تست preview بدون اعمال تغییر.
6. تست اعمال بازنویسی به‌صورت revision جدید.
7. تست خطا، timeout و پاسخ ناقص بدون تخریب داده.
8. تست مستقل‌بودن provider/config/prompt دو agent.
9. تست جلوگیری از انتشار خودکار.
10. تست عدم نشت API key در log و response.
11. تست authorization و مالکیت مقاله.

## 11. تعریف پایان کار (DoD)

UI مربوط به تولید، گزارش و preview بازنویسی قابل استفاده باشد؛ حالت Mock انتهابه‌انتها تست شود؛ provider واقعی از طریق env قابل تنظیم باشد اما برای build و تست الزامی نباشد؛ همه تست‌های اجباری گذرانده شوند؛ و README متغیرهای لازم، محدودیت‌ها و روش تست را توضیح دهد.

## 12. متن آماده برای OpenCode/Codex

> ابتدا بررسی کن feature مربوط به PRD-01 در repository پیاده‌سازی شده و تست‌های آن موفق‌اند. فایل `PRD-02-AI-Writing-and-Editorial-Tools_FA.md` را به‌عنوان تنها منبع نیازمندی feature فعلی در Spec Kit استفاده کن. مراحل واقعی specify/clarify/plan/tasks/analyze موجود در محیط را اجرا کن؛ دستورها را حدس نزن و قبل از تکمیل specification/plan سراغ کدنویسی نرو. این feature باید روی مدل داده و گردش کار فعلی سوار شود، نه اینکه آن‌ها را موازی یا جایگزین کند. استقلال WritingAgent و ReviewAgent، Mock پیش‌فرض، اعتبارسنجی schema، versioning و منع انتشار خودکار را در spec و tests صریح کن. سپس پیاده‌سازی، build و همه تست‌های مربوط را اجرا و نتیجه دقیق را گزارش کن. PRD-03 را فعلاً پیاده‌سازی نکن.
