# نقشه راه پیاده‌سازی و راهنمای استفاده از Spec Kit

این فایل مکمل سه PRD است و خودش feature جداگانه‌ای برای پیاده‌سازی نیست. هدف آن این است که OpenCode یا Codex سه قابلیت مستقل را یک‌باره با هم قاطی نکند.

## 1. ترتیب پیشنهادی

| مرحله | فایل منبع | خروجی قابل تحویل | شرط شروع مرحله بعد |
|---|---|---|---|
| 1 | `PRD-01-Core-Blog-and-Workflow_FA.md` | وبلاگ عمومی، ورود، نقش‌ها، گردش تحریریه، versioning و تست | build و تست‌های PRD-01 موفق باشند |
| 2 | `PRD-02-AI-Writing-and-Editorial-Tools_FA.md` | تولید مقاله، گزارش AI، preview بازنویسی، Mock و provider واقعی قابل پیکربندی | تست‌های PRD-01 و PRD-02 موفق باشند |
| 3 | `PRD-03-AI-Blog-Assistant_FA.md` | دستیار read-only برای پرس‌وجو و بازیابی پست‌ها | تست‌های قبلی همچنان سبز و scope دستیار محدود باشد |

هر مرحله را پس از اجرا و تست در Git commit کن. مرحله بعد باید روی همان کد سالم ساخته شود، نه بر اساس فرض اینکه مرحله قبلی کامل شده است.

## 2. روش پیشنهادی برای هر PRD

1. فایل PRD موردنظر را در repository قرار بده؛ `PRD.md` می‌تواند کپی همان فایل feature جاری باشد. بهتر است هر سه سند در پوشه‌ای مانند `docs/prd/` باقی بمانند.
2. از agent بخواه ابتدا `AGENTS.md`، فایل‌های موجود، ساختار پروژه، `.specify/` و دستورهای واقعاً نصب‌شده Spec Kit را بررسی کند.
3. فقط PRD مرحله جاری را به‌عنوان نیازمندی feature جاری معرفی کن. دو PRD بعدی صرفاً نقشه راه‌اند و نباید در scope جاری پیاده‌سازی شوند.
4. به ترتیب workflow واقعی ابزار اجرا شود: specify، clarification فقط برای ابهام واقعی، plan، tasks و analyze. دستورهای slash را از روی حدس نساز؛ از همان دستورهایی استفاده کن که در محیط نصب‌شده موجود هستند.
5. قبل از تکمیل specification و plan کدنویسی شروع نشود. معیارهای پذیرش PRD باید به task و تست مشخص تبدیل شوند.
6. بعد از پیاده‌سازی، build و همه تست‌های مرتبط اجرا شوند. خروجی باید شامل نتیجه واقعی تست‌ها، دستور اجرا، متغیرهای محیطی و موارد انجام‌نشده باشد.
7. اگر تست شکست خورد، agent باید علت را بررسی و رفع کند؛ نباید صرفاً تست را حذف یا ضعیف کند تا سبز شود.

## 3. متن عمومی پیشنهادی برای آغاز هر مرحله

در هر مرحله، ابتدا متن عمومی زیر را به agent بده و سپس متن مخصوص همان مرحله را از انتهای PRD مربوط استفاده کن:

> ما این محصول را به‌صورت مرحله‌ای با Spec Kit توسعه می‌دهیم. پیش از هر کاری دستورالعمل‌های مخزن، `AGENTS.md`، ساختار repository، فایل‌های `.specify/` و دستورات واقعی Spec Kit نصب‌شده را بررسی کن. PRD مشخص‌شده برای مرحله جاری تنها منبع scope این feature است؛ PRDهای بعدی فقط برای اطلاع از نقشه راه هستند و نباید اکنون پیاده‌سازی شوند. ابتدا specification و plan و tasks را کامل کن و analyze را اجرا کن؛ تا پیش از تکمیل این مراحل، کدنویسی را شروع نکن. هر معیار پذیرش باید به تست قابل اجرا متصل باشد. در پایان build و تست‌ها را اجرا کن و فقط نتایج واقعی را گزارش بده. اسرار واقعی نساز یا commit نکن، dependency غیرضروری اضافه نکن و اگر تناقضی در نیازمندی یا repository وجود داشت آن را صریح گزارش کن.

## 4. فرض‌های مشترک که باید ثابت بمانند

- برنامه MVP یک Spring Boot modular monolith است؛ microservices نساز.
- Java 17+، Spring Boot 3.x، Maven، Spring MVC/Thymeleaf، Spring Security و Spring Data JPA استفاده می‌شوند.
- H2 پایگاه پیش‌فرض توسعه و تست است؛ پشتیبانی PostgreSQL با profile مجزا باید حفظ شود.
- رابط اصلی MVP یک UI ساده و واکنش‌گراست؛ Swagger جایگزین UI نیست و در این scope اجباری نیست.
- اجرای Mock نباید API Key یا اینترنت بخواهد.
- عملیات حساس در service layer هم مجوزسنجی می‌شوند؛ کنترل UI به‌تنهایی کافی نیست.
- AI هیچ‌وقت خودش مقاله را منتشر نمی‌کند.
- تمام گزارش‌ها و تأییدها باید به revision مشخص متصل شوند.
- تست‌های اصلی باید deterministic باشند و به provider واقعی وابسته نباشند.

## 5. نکته درباره Swagger و تست دستی

چون این محصول وبلاگ و پنل مدیریت دارد، راه اصلی تست end-to-end در MVP باید UI باشد. تست منطق، مجوزها و workflow هم با JUnit/Spring Boot Test انجام شود. Swagger/OpenAPI را فقط در صورتی اضافه کن که نیاز واقعی به REST API برای مصرف‌کننده جداگانه ایجاد شود؛ افزودن آن نباید جای تست UI یا تست‌های امنیتی را بگیرد.

## 6. قبل از اعلام «تمام شد»

Agent باید صریحاً گزارش کند:

- دستور build و نتیجه آن.
- دستور تست و تعداد تست‌های موفق/ناموفق.
- دستور اجرای برنامه و URL محلی.
- نحوه ساخت/تنظیم مدیر اولیه برای محیط محلی.
- صفحات/سناریوهای قابل تست دستی.
- متغیرهای محیطی اختیاری و الزامی، بدون افشای secret.
- هر limitation، TODO یا بخشی که واقعاً پیاده نشده است.
